# Review Boundaries — 分层、有限变更与授权来源

本规则由 `guide`、`hld-reviewer`、`lld-reviewer`、`code-reviewer` 共用。它约束评审行为，不新建产品门禁、审批平台或必填文档集；不改变 Code Reviewer 已有 Candidate、Scope Lock、证据与漏审状态机。

## 1. 先识别任务，不能靠标题选 Skill

先用一句话说明：用户要评审的对象、当前阶段、相对哪份已批准边界发生了什么变化。`技术方案`、`工程设计`、`ADR`、`Lead Dev` 都不足以单独确定评审层级；跨仓数量、代码行数、安全关键词也不是层级依据。

| 实际需要回答的问题 | 主路由 | 不应代替的工作 |
|---|---|---|
| 业务做什么、谁能用、收费/支持/可用性承诺是否改变 | 产品决策；必要时 PRD review | Reviewer 自行决定产品范围 |
| 谁承担职责、信任谁、依赖谁、数据/控制流和失败边界是什么 | HLD review | 用类图/SQL 掩盖职责变化 |
| 已批准边界内如何实现：方法、事务、锁、SQL、重试、序列化、配置落点 | LLD review | 因跨仓或涉及安全就升级为 HLD |
| wire、身份、权限语义或兼容契约如何定义/变更 | API review 对受影响契约增量 | LLD/Code comment 代替契约批准 |
| 精确实现是否符合已批准要求 | Code Review | 在源码评审中设计新能力 |

混合请求按问题拆分，不把整份修复计划升级为 HLD：边界内部分继续 LLD/Code，只有真实的架构/契约增量交对应层级。没有实现 Candidate 的方案不能签 Code Review；已有代码也不让尚未批准的设计自动生效。

## 2. 正式设计与有限变更是两种入口

- `formal_design`：用户提交完整新功能 HLD/LLD 准出，执行该层级完整覆盖与追溯检查；不能借有限模式绕过已要求的正式设计。
- `bounded_change`：已有系统的 bugfix、兼容修复、ADR 增量或范围明确的工程修复计划。读取可取得的相关批准需求/Contract/HLD/ADR/用户决定和实现事实，审查受影响链路。接受现有修复说明，不强制新写全套 PRD/HLD/LLD Manifest、Test Strategy、Test Spec、Runbook 或 certificate。
- 整改复审继承原问题 ID、范围和验收语义，只审 delta、原阻断项及直接影响；上轮未审/缺证部分需明确补审，不虚称已覆盖。不因切换 skill 或升级规则重开全部历史范围。

有限模式也必须有可确认的行为依据。缺少某种文件格式，不等于行为依据缺失；旧源码/现网只是事实，不能单独证明设计获批。关键依据确实不明时只暂停依赖该依据的结论，继续其他可独立判断部分。

## 3. 基线来源不能循环自证

对争议或新增边界，沿引用回到原始批准记录，简要说明**谁在什么范围内批准了什么**。可引用用户原话或现有 ADR/批准记录及版本；不强制新造哈希账本。

下列材料不能独立充当新增范围授权：作者 note、测试 PASS、当前实现、Reviewer 自己的旧 comment、由该 comment 抄写的“APPROVED”文档、没有权限来源的 Lead Dev 头衔。不能把这些材料再冻结为基线后要求开发服从。

若发现过去已存在这种污染，披露具体来源与受影响结论，撤回该部分的“已批准”表述；不要暗中改成新基线，也不要自动撤销无关的有效批准。按冲突/待决策处理，不为了守住错误冻结范围继续扩大实现。

## 4. 技术合理性、设计授权、执行许可分别判断

1. **技术合理性**：方案能否解决已证实问题，有无更小的边界内方案。
2. **设计授权**：是否属于已批准范围或明确授予的工程决策权限。
3. **执行许可**：是否允许改代码、push、CI、发布策略/配置、写共享数据或部署。

“推荐”“技术可行”“P1 请修复”“设计评审通过”不自动授予另外两层权限。Reviewer 可以评估尚待裁决的方案，不能伪装成已经准出；有明确工程授权且不改变产品承诺的细节可直接裁定，不把每个 SQL/锁选择都上交产品经理。

这不要求待审 HLD 先取得一次相同的 HLD 批准。正式新功能在已批准需求、项目约束和工作流授予的设计准出权限内，可以完成技术选型与设计评审；原始权限来源也可以是明确的项目治理约定。只对超出该授权的增量要求额外决定，不给正常 Design Review 再套一层默认审批。

下列变化即使**没有新增表、接口或服务**也要核对架构授权：

- 机器后台任务改成依赖人的成员资格/在线会话/用户 PDP，或反向改成人工授权之外自动放行。
- 更换谁能授权、签发、读取或删除什么；改变职责 owner、信任模型、权限管理来源。
- 增加常态外部依赖、策略管理步骤、运行费用/人工维护，或改变依赖失败时业务能否继续。
- 以兼容/测试/安全为名改变已批准数据范围、生命周期、失败语义或产品支持边界。

`技术必要性` 是待举证理由，不是授权豁免。最佳实践、复用现有组件、安全更严格、测试能通过都不能替代批准。必要性必须关联既定 invariant、真实失败路径、边界内替代方案及额外运行负担；不要为了“更安全”自动增加 PDP，也不要为了“避免加料”删除已批准的安全检查。

## 5. 缺陷、证据缺口、设计决定与建议分栏

- **缺陷**：明确违反有效基线，能指出具体失败路径和影响；按实际严重性列 P0/P1，最小修复保持边界。未批准扩张可直接退回既有明确边界时，优先要求退回，不诱导用户批准更多范围。
- **Evidence gap**：必要事实/可行性未证实，不捏造缺陷或 PASS。给最小缺失证据；不要用更复杂实现代替取证。
- **Scope decision**：基线冲突、真实所需修复超出授权，或提交的方案明确请求改变边界。说明旧/新行为、影响、边界内选项和建议，由有权 Owner 决定；涉及产品行为、权限对象、支持范围、收费/数据处置等由产品 Owner 裁定。纯架构变化交有明确授权的工程 Owner，权限来源不明再请用户指定。只暂停依赖该决定的部分。
- **P2**：可选改进，数量永不阻断，不自动结转为下轮必须整改。发现数量不是评审质量指标。

每条强制 comment 至少写清：有效依据、当前失败、影响、最小修复、是否改变边界；若不能在已有授权内提出修复，就标为待决定，而非把新设计塞入 P1。

HLD/LLD 输出分别列 `technical_verdict`（`APPROVED / CHANGES_REQUIRED / EVIDENCE_BLOCKED`）与 `scope_status`（`WITHIN_APPROVED_SCOPE / DECISION_REQUIRED`）。技术上合理而边界待批准不能总称准出。有限评审只给该增量的意见，不签全量设计证书；正式证书需覆盖完成、无 P0/P1、无必要证据/授权缺口。Code Review 继续使用自身 verdict precedence。

## 6. 可行性必须覆盖真实管理入口

对修复直接依赖的权限/策略/SDK/部署能力，区分：调用方输入 → 真实管理入口及其可表达格式 → 实际解释/执行器 → 业务结果。自写 compiler、模拟管理 API 或直接构造执行器输入不证明现有管理入口能产生同样配置。

优先用既有生产 client/parser、已知生产样本、官方契约或最小隔离实验核实关键能力；不要求一律操作现网或搭新平台。若真实入口拒绝拟议输入，属于可行性问题，不得仅列为“部署后补配置”。离线无法验证时准确限定证据，保留最小 gap；没有现网验证本身也不等于源码错误。

## 7. 可持续停止条件

本轮已约定范围内的 P0/P1 与必要 gap 关闭即停止；不靠 P2、未来需求、模板美化或新增验证平台续轮。范围外发现独立记录，不自动加入本轮。评审者此前漏审或错误决策须说明责任，不把旧错误包装为 Dev 新缺陷；源码场景仍服从 Code Reviewer 的有限漏审机制。

这些规则约束评审者，不给产品增加一套发布系统、常设审批角色或新的测试文档要求。记录优先复用现有请求/回复，能够直接说清的结论不强制生成表格或文件。
